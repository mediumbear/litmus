== Overview and the Main Types

:litmus-dir: src

This book is the source of Litmus. Tangle it and you get the program; build the program and it tangles this book again, to the same bytes. The chapters follow the journey of a document through the program, and each chapter holds the files that do one step of that journey.

[[pipeline]]
Litmus has one pipeline, and every command uses a part of it:

....
document text
    scan      (chapter 2)   classify each line: prose, command, block edge, code, ...
    parse     (chapter 3)   labels, blocks and excerpt commands of one document
    docset    (chapter 4)   follow include:: and put the documents in reading order
    resolve   (chapter 5)   group blocks into files and excerpts, and run the checks
    tangle    (chapter 6)   expand each file and record where its lines came from
    map, output (chapter 7) write the files and the map, without losing anyone's work
    commands  (chapter 8)   tangle, check, where, guide, init, untangle, sync, watch, style
    untangle  (chapter 9)   carry edits of the files back into the documents
    adopt     (chapter 8)   a new document from files that have none
....

The spec, `doc/litmus.adoc`, says what Litmus does. This book says how. Every behaviour traces to a rule of the spec, and the tests in this book name the rule they check: L for the language, T for tangle, C for the checks, M for Markdown and I for init. When the code needs something the spec does not say, the spec changes first.

=== Four decisions that shape the code

Litmus runs on every save, so it has to be fast. It also has to be dependable, since the files it writes are the files a compiler reads. Four decisions follow from that.

Read each document once, and keep the lines as slices of the text::
A document is read into one buffer and cut into lines, but no line is copied. Blocks, labels and excerpt commands point into the buffer. Nothing is parsed twice.

One arena per run::
Everything lives until the program ends, so nothing is freed one piece at a time. The program asks the operating system for memory in large steps and never gives it back until it exits. This is simple, and fast.

No regular expressions::
The syntax is a handful of line shapes. Looking at the first bytes of a line is enough, and it is faster and easier to read than a pattern.

Report everything::
A writer fixing a document wants the whole list of mistakes, not the first one. Each stage records a diagnostic and goes on. A diagnostic is printed as `document:line: message`, in the order of the document set.

The exit code is 0 for success, 1 for errors or differences, and 2 for wrong usage.

=== The main types

All stages share a few types. They are collected in one file, so that a stage can be read without opening the one before it. All of them are allocated in the run's arena, and the lines they hold are slices into the documents' text.

A `Document` is a path, a format, and the document's lines. Its `dir` is the directory that contains it, which is where `include::` paths start (L6). Not to be confused with `:litmus-dir:`, which sets where tangled files go (L8). `final_newline` remembers whether the text ended with a newline. `style` is the style file that applies to the document (L10), its own or one it inherits, and `companion` says whether the document marks itself a companion of its code (L11). The lines alone cannot say, and untangle must write a document back exactly as it was.

A `Label` is what a document command says (L1, L9). It records where the label is, so that later errors can point at it. The `file` is the full path of the file the block lands in, with the document's `:litmus-dir:` already in front. A file root has no name.

A `Run` is the map's unit. While tangle expands a file, it notes each stretch of consecutive output lines that came from consecutive lines of one block, with the same indent. The map is a list of runs, and so is the answer to "where did this line come from".

Two more fields are for untangle, and are not in the map: the block the run's lines are lines of, and the expansion the run is in, which is explained next. The map is made from the first six fields only.

/// A run of consecutive lines of a tangled file that come from consecutive lines of
/// one block, with the same indent (the map's lines).
pub const Run = struct {

    line: u32,
    count: u32,
    doc: u32,
    doc_line: u32,
    indent: u32,
    /// The excerpt's name, or `:file:` for the file root.
    excerpt: []const u8,
    /// The expansion the run's lines are in, as an index into the file's expansions,
    /// or `no_expansion` for the file root. Untangle needs it; the map does not.
    expansion: u32 = no_expansion,
    /// The block the run's lines are lines of.
    block: ?*const Block = null,
};
----

An `Expansion` is one excerpt command, as tangle expanded it. It records the output lines the command produced, the block that holds the command and the command's place in it, and the indents: the command's own and those of the commands around it, put together, with how many of the bytes belong to the ones around. Untangle uses expansions to decide where a line that was added between two runs belongs, and what indent it has to carry. They live only in memory.

A run in the file root is in no expansion, and says so with `no_expansion`.

`Diagnostics` collects them. The messages are formatted into the arena as they are added. Before they are printed they are sorted by document, then by line, so that the report follows the reading order whatever order the stages found the problems in. The sort keeps the order of problems on one line, because Zig's `std.mem.sort` is stable.

… Diagnostics :file: types.zig
[source,zig]
----
pub const Diagnostics = struct {
    arena: std.mem.Allocator,
    list: std.ArrayList(Diagnostic) = .empty,

    pub fn init(arena: std.mem.Allocator) Diagnostics {
        return .{ .arena = arena };
    }

    pub fn add(self: *Diagnostics, doc: u32, line: u32, comptime fmt: []const u8, args: anytype) !void {
        const message = try std.fmt.allocPrint(self.arena, fmt, args);
        try self.list.append(self.arena, .{ .doc = doc, .line = line, .message = message });
    }

    /// Orders the diagnostics by document, then line, keeping the order of equal ones.
    pub fn sort(self: *Diagnostics) void {
        std.mem.sort(Diagnostic, self.list.items, {}, less);
    }

    fn less(_: void, a: Diagnostic, b: Diagnostic) bool {
        if (a.doc != b.doc) return a.doc < b.doc;
        return a.line < b.line;
    }
};
----
