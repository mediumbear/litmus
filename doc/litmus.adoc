= Litmus
:toc: left
:toclevels: 2
:sectanchors:

Litmus turns a document into source code, and changes in the source code back into the document. The document is asciidoc, written to be read: prose that explains, with the code in the order that explains it best. Litmus adds one thing to asciidoc, the _Litmus command_: a line that starts with `…`.

There are three operations:

tangle:: Document to source files.
untangle:: Changes in the source files back into the document.
weave:: Document to a page for reading. Asciidoctor does most of this.

== How Litmus is used

Code is written and tested in the source files, as usual. Untangle carries the changes into the document, and the writer then writes prose for any new code. Tangle proves that the document still holds the code: tangling it must give the source files byte for byte.

A person mostly reads the document, and edits its prose. Prose never affects the code.

This order suits an agent writing the code, which needs a compiler and tests in the loop, and a person who wants to read the result and understand the whole picture.

== An example

....
The program prints a greeting from its main function.

… :file: hello.zig
[source,zig]
----
… imports

pub fn main() void {
    … greet
}
----

The greeting goes to standard error, which needs no setup:

… greet :file: hello.zig
[source,zig]
----
std.debug.print("Hello, Litmus!\n", .{});
----

… imports :file: hello.zig
[source,zig]
----
const std = @import("std");
----
....

Tangling it gives `hello.zig`:

[source,zig]
----
const std = @import("std");

pub fn main() void {
    std.debug.print("Hello, Litmus!\n", .{});
}
----

Every label says which file its block lands in. On the page, each `…` line shows as a short plain paragraph above its block, so the document reads well even before weaving.

== Terms

Litmus command:: A line whose first character, after any spaces and tabs, is `…` (U+2026, the ellipsis), followed by a space.
Code block:: An asciidoc listing block, opened by a line of four or more hyphens and closed by the same line. Or a fenced block, opened by `+```+` with an optional language, and closed by `+```+`.
Document command:: A Litmus command outside code blocks. It labels the code block that follows it.
Excerpt:: The code of all blocks labeled with the same name and the same file, joined in document order.
Excerpt command:: A Litmus command inside a labeled code block. It stands for an excerpt, inserted at that point.
File root:: The code of all blocks labeled `… :file: path` with no name, joined in document order. Each file is tangled from its root.
Illustration:: A code block without a document command. It is shown, never tangled.
Document set:: The documents named on the command line, and the documents they include, in reading order.

== Syntax

*Rule L1.* A document command is either `… name :file: path`, which labels a block of an excerpt, or `… :file: path`, which labels a block of a file root. Every document command names its file.

* A name is the text before `:file:`, with surrounding spaces removed. It may contain spaces. It may not start with `:`.
* A path is relative and uses `/`. It has no `..` parts and does not start with `/`.

*Rule L2.* A document command labels the code block that starts after it. Between the two there may be only block attribute lines, such as `[source,zig]`, and a block title line, such as `.The dispatch loop`. A label must sit next to its block.

*Rule L3.* An excerpt command is `… name`, alone on its line, inside a labeled block. Whatever comes before the `…` is the command's indent.

*Rule L4.* In a labeled block, every Litmus command is an excerpt command. A line of code cannot start with `…`. The ellipsis character is rare in code.

*Rule L5.* Litmus commands are ignored in illustrations, in literal blocks (`....`), comment blocks (`////`), passthrough blocks (`++++`), and on comment lines (`//`). That is how a document such as this one can show Litmus in its examples.

*Rule L6.* An `include::path[]` line outside any block adds the included document to the document set at that point. Its path is relative to the including document. An `include::` inside a labeled block is an error: asciidoctor would paste the file's text into the block on the page, which tangle does not do.

*Rule L7.* A line ends at `\n`. Everything else, including a `\r`, is part of the line.

*Rule L8.* A document may set a directory for its paths with the attribute entry `:litmus-dir: src/core`, on a line of its own, outside blocks, before its first document command. Every `:file:` path in that document is then taken inside that directory: `… :file: vm.zig` means `src/core/vm.zig`. It applies to that document only, not to the documents it includes, so a block's file never depends on where the block sits. The directory follows the same rules as a path in L1.

*Rule L9.* A file-root label may end with `:executable:`, as in `… :file: scripts/build.sh :executable:`. The file is then written with permission to run it. One such label is enough for the file.

*Rule L10.* A document may name a style file with the attribute entry `:litmus-style: style.md`, on a line of its own, outside blocks, before its first document command. The path is relative to the document, like an include, and may go up with `..`. The style file says who the reader is and how prose and pictures are done, for whoever writes the document's prose, person or agent. An included document uses the style of the document that includes it, unless it names its own. Style never changes code: tangle ignores it.

*Rule L11.* A document may say `:litmus-companion:`, on a line of its own, outside blocks, before its first document command. The document set is then a companion of the code: see <<companion>>.

A listing block closes only at a line equal to the one that opened it. Code that contains a line of four hyphens, such as a Lua comment, goes in a block opened with five or more.

== Tangle

*Rule T1.* A file's text is its file root, with every excerpt command expanded.

*Rule T2.* An excerpt command is replaced by its excerpt's lines, each expanded in turn, each with the command's indent put in front. Empty lines stay empty.

*Rule T3.* Every line of a file ends with `\n`, the last one included.

*Rule T4.* Tangle writes a file only when its text changed, so builds and watchers see only real changes. It writes each file whole, under a temporary name, and then renames it, so nothing ever reads half a file.

*Rule T5.* Tangle never deletes a file. A file that the previous map lists but the documents no longer tangle is reported, and left where it is.

*Rule T6.* Tangle never overwrites a change it did not make. Before writing a file that exists, it compares the file with the hash the map recorded when tangle last wrote it. If they differ, the file was changed since, and tangle reports it and writes nothing at all. A file the map does not list is treated the same way, unless it already equals its tangled text. `--force` overwrites anyway.

T6 protects the usual case: someone edits a tangled file, the change is not in the documents yet, and tangle runs. Without T6 the edit would be lost.

== Checks

Each of these is an error, reported as `document:line: message`. If there is any error, tangle writes nothing.

*Check C1.* An excerpt command names an excerpt that has no blocks in the file being tangled. This includes an excerpt labeled with a different file.

*Check C2.* An excerpt is not used by any excerpt command.

*Check C3.* An excerpt is used by more than one excerpt command.

*Check C4.* An excerpt contains itself, directly or through other excerpts.

*Check C5.* A document command is not followed by a code block (L2).

*Check C6.* A code block is still open at the end of its document.

*Check C7.* A path breaks L1 or L8, or an `include::` breaks L6. A path may also not contain a tab, since the map separates its fields with tabs.

*Check C8.* A `:litmus-dir:`, `:litmus-style:` or `:litmus-companion:` comes after a document command, or appears twice in one document.

*Check C9.* `:executable:` is on an excerpt's label rather than a file root's.

*Check C10.* A document includes itself, directly or through other documents, is in the document set twice, or names a document that does not exist.

*Check C11.* A document command has no `:file:`, has `:file:` twice, has an attribute other than `:file:` and `:executable:`, or has a name that starts with `:`.

*Check C12.* The style file that a document names does not exist.

C2 and C3 together mean that every excerpt is used exactly once. Then every line of every file comes from exactly one line of the document set, and every line of labeled code lands in exactly one place. Tangle can be run backwards, which is what makes untangle exact.

Names belong to their file. Two files can each have an excerpt called `body`. An excerpt command in a file's code only finds excerpts labeled with that file.

Since every label names its file, a reader or an agent knows where a block lands from its label alone, without tracing excerpt commands back to a root.

== The Map

Tangle writes `.litmus/map` in the output directory. For every line of every tangled file, it says where the line came from, and it records what tangle last wrote (T6). The map is not committed. Losing it loses nothing: tangle then accepts a file that equals its tangled text as unchanged.

The map is text. The first line is `litmus map 1`. Each file starts with a line of three fields separated by tabs: `file`, its path, and the SHA-256 of the text tangle wrote, in lowercase hexadecimal. Then one line per _run_, a group of consecutive lines of the file that come from consecutive lines of one block. A run has six fields, separated by tabs:

[cols="1,3",options="header"]
|===
| Field | Meaning
| line | The run's first line in the file, counting from 1.
| count | How many lines the run has.
| document | The document the run comes from.
| document line | The line of the document where the run starts.
| indent | How many bytes were put in front of each non-empty line (T2).
| excerpt | The excerpt's name, or `:file:` for the file root.
|===

The map for the example, if its document is `hello.adoc`:

....
litmus map 1
file	hello.zig	2bc975ea988a6520d4c5937fbec6d64a98ce153bb2dc852c50affe981da286c2
1	1	hello.adoc	24	0	imports
2	2	hello.adoc	7	0	:file:
4	1	hello.adoc	18	4	greet
5	1	hello.adoc	10	0	:file:
....

== Commands

`litmus tangle [-o DIR] [--force] DOCUMENT...`::
Tangles the document set into files under `DIR` (the current directory by default), and writes the map. `--force` overwrites files changed since the last tangle (T6).

`litmus check [-o DIR] DOCUMENT...`::
Tangles in memory and compares the result with the files under `DIR`. For each file that differs or is missing, it prints the first line that differs and where that line is in the document. It exits with 1 if any file differs. This is the round-trip check, run after every change.

`litmus where [-o DIR] [DOCUMENT] FILE:LINE`::
Reads the map under `DIR`, or the map of the companion `DOCUMENT` (R2), and prints the document line that `FILE:LINE` came from, as `document:line (excerpt)`, with `(file root)` for the root of the file. This turns a compiler error into a place in the document.

`litmus guide`::
Prints the guide for agents, below.

`litmus init [-o DIR] DOCUMENT...`::
Prepares the project in the current directory for agents. See <<init>>.

`litmus untangle [-o DIR] [-f FILE]... DOCUMENT...`::
Carries the changes in the source files back into the documents, and reports where prose is needed. See <<untangle>>.

`litmus sync [-o DIR] DOCUMENT...`::
Does whichever of tangle and untangle the state of the files and the documents calls for (U7). It exits with 1 if both changed.

`litmus watch [-o DIR] [--interval MS] DOCUMENT...`::
Runs sync now, and again whenever a file changes. See <<watch>>.

`litmus adopt [-o DIR] [--companion] [--style FILE] DOCUMENT PATH...`::
Writes a new document that holds the code of existing files. See <<adopt>>.

`litmus style DOCUMENT...`::
Prints, for each document of the set, the style file that applies to it (L10), or `none`.

*Rule N1.* Untangle, sync and watch end what they print with a line that starts with `next:` and says what to do next, in words an agent can act on: which prose to write and in which style, what to revert, or that nothing is left to do.

Document paths are recorded in the map as they were given, so Litmus is run from the same directory each time, normally the project's root.

[[guide]]
== The Guide

Agents learn how to work in a project that uses Litmus from `litmus guide`. The text comes with the installed Litmus, so it always matches the version in use. `litmus guide` prints exactly this:

....
include::../src/guide.txt[]
....

[[init]]
== Init

`litmus init [-o DIR] DOCUMENT...` sets up the project in the current directory so that agents find the guide. It takes the same `-o` and documents as tangle.

*Rule I1.* In `AGENTS.md` it adds this paragraph, or replaces the one a previous init added, found by its two comment lines:

....
<!-- litmus -->
This project uses Litmus: some source files are tangled from documents that
explain them. Run `litmus guide` before changing any file listed in
DIR/.litmus/map. After editing a tangled file, carry the change into the
documents with `litmus untangle -o DIR DOCUMENT...`, and write the prose it asks for.
Tangle with `litmus tangle -o DIR DOCUMENT...`, and make sure
`litmus check -o DIR DOCUMENT...` passes before finishing.
<!-- /litmus -->
....

`DIR` and `DOCUMENT...` are filled in from the command. When `DIR` is the current directory, the `-o DIR` and the `DIR/` are left out. `litmus` is replaced by the path init was run with, when that path contains a `/`, so the line works when Litmus is not on the `PATH`.

*Rule I2.* In `CLAUDE.md`, the file Claude Code reads, it adds a line `@AGENTS.md`, which imports `AGENTS.md`, unless a line already does.

*Rule I3.* In `.gitignore` it adds `DIR/.litmus/`, or `.litmus/` when `DIR` is the current directory, unless a line already says so.

*Rule I5.* It writes the skill `litmus-document`, which tells an agent how to make a literate document for existing code (see <<adopt>>), to `.claude/skills/litmus-document/SKILL.md`, where Claude Code finds it. The skill comes with Litmus, so an older copy is replaced.

*Rule I4.* Init creates any of these files that are missing, changes nothing else, and prints each change it makes. Running it twice changes nothing the second time.

[[untangle]]
== Untangle

Untangle carries changes made in the tangled files back into the documents. The writer, or the agent, edits and tests the code in the source files as usual, runs `litmus untangle`, and the blocks of the documents hold the change. The prose is still the writer's: untangle reports where it is needed.

It works because every line of a tangled file comes from exactly one line of the document set (C2, C3), and the map says which. Whatever it does, it ends with a check (U9), so the documents it writes always tangle to the files.

An example. After tangling the document of the example above, a writer edits `hello.zig`. The greeting changes, and a line is added to `main`:

[source,zig]
----
const std = @import("std");

pub fn main() void {
    std.debug.print("Hello, world!\n", .{});
    std.debug.print("Bye.\n", .{});
}
----

The changed line came from the block of `greet`, so the block changes (U3). The added line sits between two lines of different runs: the end of `greet` and the `}` of the root block. It goes after the command `… greet` in the root block, where the indent of the line allows it (U4). Untangle prints:

....
changed 1 line, removed 0 lines, added 1 line, in 1 document
needs prose: hello.adoc:3 (file root of hello.zig) grew by 1 line
placed at a boundary: hello.zig:5 went after "… greet" at hello.adoc:9
....

*Rule U1.* The base is the document set tangled in memory. If the base equals the source files, there is nothing to do. If the base differs from what the map says tangle last wrote, the documents changed as well, and untangle stops (U7).

*Rule U2.* Each file of the base is compared with the source file, line by line.

*Rule U3.* A changed or removed line is changed or removed at the document line it came from. A source file that the map lists but that is missing is reported, and left alone.

*Rule U4.* A line added between two lines of the same run goes into that block, at that place. A line added anywhere else goes into the block that holds an excerpt command, next to that command: after it where an excerpt ends, before it where an excerpt begins. If several commands are at that place, the innermost one whose block's indent the line starts with is taken. An empty line goes with the outermost. A line added at the start or the end of a file, or between two blocks of one excerpt, goes at the start of the block that follows, or at the end of the block that comes before. Every such line is listed in the report, since the writer may want it elsewhere.

*Rule U5.* A changed or added line inside an excerpt that no longer starts with the excerpt command's indent is reported, not guessed. If anything is reported, untangle writes nothing.

*Rule U6.* Untangle reports every block that grew, as _needs prose_. That list is the writer's work before a change is done.

*Rule U7.* The map decides the direction, and `litmus sync` follows it. Files differ from the map if their hash is not the one the map recorded. Documents differ from the map if the document set tangled in memory has a different hash. If only the files differ, untangle. If only the documents differ, tangle. If both differ, stop and report the files and the excerpts involved. Prose changes never count. Without a map, a file that equals its tangled text is unchanged, and a file that differs is reported, since the direction is not known.

*Rule U8.* A source file named with `-f` that is not in the map is reported. Untangle does not invent a document for it. Untangle looks only at the files in the map and those named.

*Rule U9.* Untangle writes the documents only if the edited documents, tangled in memory, equal the files on disk byte for byte. Otherwise it reports the first difference and writes nothing.

[[watch]]
== Watch

`litmus watch` keeps the documents and the files in step while the writer works. A save of a tangled file or of a document is followed, a moment later, by whichever of tangle and untangle the change calls for (U7). The rules say when that happens.

*Rule W1.* Watch runs sync once at the start. After that it runs sync whenever a watched file has changed and then stayed unchanged for one interval, so a formatter that rewrites many files, or an editor that saves in steps, causes one run.

*Rule W2.* The watched files are the documents of the document set and the tangled files. The set is worked out again after every run, since an include may have been added or removed.

*Rule W3.* A change is a difference from what was seen last in whether the file exists, its size, or its modification time. Files are looked at once every interval, 200 milliseconds unless `--interval` says otherwise.

*Rule W4.* What Litmus writes during a run is not a change. The watched files are looked at again when the run is over, and that is what later looks are compared with.

*Rule W5.* If a run stops, because both sides changed or a document has an error, watch prints why and waits for the next change. It does not run again by itself, and it never forces.

Each run is printed as a block: a heading with the seconds since watch started and the files that changed, and then what sync says. Nothing is printed when a look finds no change. Watch runs until it is stopped.

[[companion]]
== Companion Documents

A companion document explains code that it does not own: code someone else wrote, or code an agent wrote, that a reader wants to understand. It must never write to that code, and it must follow the code as the code moves on.

*Rule R1.* A document set is a companion if any of its documents says `:litmus-companion:` (L11).

*Rule R2.* A companion's map is kept in `.litmus/map` in the directory of the first document named on the command line, not under `DIR`. Nothing is ever written under `DIR`. The map holds document lines, so it is rewritten whenever the documents moved and nothing else changed, such as when prose was written or blocks were moved: untangle and sync do so when they find nothing to carry over.

*Rule R3.* Tangle refuses to tangle a companion.

*Rule R4.* Untangle and check work as for any document set. Untangle is how a companion follows the code: a change in the code is carried into the document.

*Rule R5.* If a companion's code was changed in the document, sync and watch do not tangle it. They report it, and say to undo the change in the document, or to run `untangle --force`, which takes the code's version.

[[adopt]]
== Adopt

`litmus adopt` writes a new document from code that has none, as the start of a literate document. The code is split into excerpts, so that a writer, person or agent, can reorder them and write prose around them. The document holds every line of the code, so it passes `check` at once.

*Rule A1.* Each `PATH` is relative to `DIR`. A folder stands for the files in it, found recursively and taken in sorted order. Entries whose name starts with `.`, the folders `zig-out`, `build`, `DerivedData`, `node_modules` and `Pods`, and files that hold a zero byte, are skipped.

*Rule A2.* Adopt refuses to write a document that exists, and refuses a file that cannot go into a block: one with a line that starts with `…` after spaces and tabs (L4), one with a line that starts with `include::` (L6), or one that does not end with a newline (T3). Before it writes anything, adopt tangles the new document in memory and requires every file back, byte for byte.

*Rule A3.* Each file becomes a section whose title is its path, with a file root and excerpts. A line `// MARK: - Title` or `// MARK: Title` becomes a subsection with that title, where it falls between excerpts.

*Rule A4.* At the top level, an excerpt starts at a line that begins with neither a space nor a tab, nor `}`, and that follows a blank line. Comment lines directly above a declaration stay with it.

*Rule A5.* A top-level excerpt of more than 40 lines whose first line ends with `{`, and whose last line is `}` or `};`, is split one level deeper. Inside it, an excerpt starts at a line that has the indent of the first non-blank line of the body, follows a blank line, and is not a closing brace. Each such excerpt is inserted by an excerpt command at that indent.

*Rule A6.* An excerpt is named after its first line: the first word that is not a keyword or a modifier, with punctuation after it removed. Keywords and modifiers are words such as `pub`, `fn`, `const`, `var`, `let`, `func`, `struct`, `class`, `actor`, `enum`, `extension`, `protocol`, `init`, `public`, `private`, `fileprivate`, `internal`, `static`, `final`, `override`, `mutating`, `nonisolated`, `export`, `extern`, `inline`, `test`, and attributes such as `@MainActor`. A member is named `Type.member`. A test is named after its string. A name already taken in the file gets a number.

*Rule A7.* Each block opens with a line of hyphens one longer than the longest line of only hyphens in its code, and at least four.

*Rule A8.* The document names its style file if `--style` is given (L10), and says `:litmus-companion:` if `--companion` is given (L11). Adopt then writes the map, under `DIR`, or beside the document for a companion (R2), so that untangle, sync and watch work at once.

== Weave

Asciidoctor with a small extension, `doc/litmus-weave.rb`. A document command becomes a small label with its file name and an anchor. An excerpt command becomes a link to its excerpt, and the label links back. The table of contents follows the section being read. Diagrams in `<pre class="mermaid">` passthrough blocks are drawn by Mermaid.

*Rule V1.* If the main document names a style file, the weave reads the `key: value` lines in its `## Settings` section. `mermaid-theme` sets the theme of the diagrams.

== Markdown

A document whose name ends in `.md` is read as Markdown. The commands and the rules for tangling are the same. What differs is how blocks are found.

*Rule M1.* A code block is a fenced block: opened by three or more backticks or tildes, with an optional language, and closed by a line of the same character at least as long. Indented code is not a code block for Litmus.

*Rule M2.* A document command labels the fenced block on the next line. Markdown has no attribute or title lines to put between them.

*Rule M3.* Litmus commands are ignored in unlabeled fenced blocks and inside HTML comments.

*Rule M4.* Markdown has no `include::`. Each Markdown document is named on the command line.

*Rule M5.* A Markdown document sets its directory with a line `<!-- :litmus-dir: src/core -->`, under the same rule as L8.
